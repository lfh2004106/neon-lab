## 先记住：一次只改一个地方

把“应该出现什么”“实际出现什么”“这次改了什么”写在一起。按供电与接线、通信与级联、方向、图案映射的顺序缩小范围；不要同时改电线、图案和程序。

## 1. 完全不亮，或只有部分模块亮

| 现象 | 下一步检查 | 暂时不能下的结论 |
| --- | --- | --- |
| 全亮自检没有出现 | 断电核对 VCC、GND、输入端及信号线；确认程序已上传 | 不能只凭全黑认定电源坏了 |
| UNO 电源灯亮，点阵黑 | 检查模块是否获得正确供电，再核对 DIN、CLK、CS | 板子亮灯不代表模块通信正常 |
| 前几片亮、后几片黑 | 检查 DOUT→DIN 级联、连接、供电和 `CHIPS = 4` | 不直接判定某片损坏 |
| 暗、闪烁、反复重启 | 检查接触、短路、供电能力，再降低亮度验证 | 不用固定电流估算代替实际检查 |

改线前断电。外部电源按模块和开发板规格连接、共地，避免向 USB 回灌。拔掉数据线后“是否全黑”不能作为供电正常的充分证据。

## 2. 形状对，方向不对

上下颠倒时，可以测试 `FLIP_Y`。左右方向则要区分“每片内部的列方向”和“四片的排列顺序”。当前源码中的 `FLIP_X` 只改变每片内部的列方向，没有反转四片的顺序。

爱心左右对称，不适合单独验证左右映射。用位置明确的不对称标记，例如预期位于 `(1, 2)` 的亮点，再逐片对照实际位置。

## 3. 两块亮斑，不像爱心

这是原项目的主要问题：中间两片亮了，但左右两部分形状不符合预期。调亮度、缩窄图案、检查接缝，都没有直接解决它。

最终修复集中在 `show()`：软件按列存像素，发送前需要重新组装模块所需的行数据。

```cpp
for (uint8_t r = 0; r < 8; r++) {
  uint8_t bits = 0;
  for (uint8_t b = 0; b < 8; b++) {
    if (canvas[c * 8 + b] & (1 << r)) bits |= (1 << b);
  }
  maxWrite(c, r + 1, bits);
}
```

用预期坐标和实测坐标来验证修复。照片里的形状还会受到透视、曝光和拍摄角度影响，不能只凭“左右两块方向相反”就唯一确定原因。

原文提到 L 形测试的局限：**是否能识别转置，要看具体图形是否在该变换下保持不变。** 不能把所有 L 形都归为“测不出来”；主对角线也不能单独排除转置。

## 4. 偏移、缺灯

- 位置偏移：检查字符画每行是否都是 32 个字符；爱心最宽 12 列的那一行，两侧各有 10 个 `.`。
- 固定位置不亮：对比全亮测试、单点测试和目标图案，继续排查写入地址、接线与器件；不要一次观察就判定 LED 损坏。
- 全亮正常但图案不对：优先核对行列、片序和方向，不能把全亮当作映射正确的证明。

## 5. 编译或上传失败

| 提示 | 先检查什么 |
| --- | --- |
| 找不到串口 | USB 数据线、实际端口、驱动；驱动型号取决于板上的 USB 转串口芯片 |
| `ser_open(): can't open device` | 端口是否存在、是否被串口监视器或其他程序占用 |
| `stk500_recv()` | 板型、端口、连接和复位等可能原因 |
| `was not declared` | 拼写、作用域、声明和完整报错上下文 |
| `expected ';'` | 报错行及其前面的语句 |

把完整错误信息保存下来。网站只展示源码，本次导入没有替你重新编译或烧录。

## 一分钟自查

- 电源与引脚已按模块规格核对，改线时已断电。
- UNO R3 的 DIN→D11、CS→D10、CLK→D13，GND 共地。
- `CHIPS = 4`，字符画八行、每行 32 个字符。
- Arduino IDE 选择实际开发板和串口。
- 记录了本次唯一改动，以及修改前后的现象。

这份笔记最值得保留的方法是：**“哪一颗灯不对”，比“看起来不对”更容易找到答案。**
