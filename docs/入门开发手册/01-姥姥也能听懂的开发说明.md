# 想象我们一起开了一间小店

小店叫“Spark 的日记”。门口有一个会转的地球，里面有两间主要的房间：一间做电子实验，一间练英语。实验心得放在工作间里的日记本中。

客人用手机或电脑打开网址，就像走进店里。**浏览器**是帮客人把店面展示出来的工具，例如 Edge 或 Chrome。

## 门面是怎么搭起来的

我们要做三个决定：摆什么、怎么摆、点了之后干什么。

| 需要做的事 | 程序里的名字 | 最小例子 |
| --- | --- | --- |
| 写标题、放图片、安排链接 | HTML，内容的骨架 | 页面上有一个“我的 GitHub”链接 |
| 决定颜色、大小、间距 | CSS，摆放和装修规则 | 这个链接穿一件浅绿色外套 |
| 回应拖动、点击、输入 | JavaScript，操作说明 | 拖动星球，改变将要去的页面 |

例如下面这一行 HTML：

```html
<a href="./embedded.html">去我的工作间</a>
```

`<a>` 表示链接；`href` 后面是目的地；中间的中文是给人看的名字。`./` 表示从当前文件所在的位置寻找。这一行不用 AI、不用数据库，浏览器自己就会处理跳转。

CSS 可以像这样给它装修。下面是教学小例子，不需要直接粘进当前网站：

```css
a {
  color: #b7e8de;
  font-size: 16px;
}
```

颜色值是颜色的编号，`16px` 是字号。先认得这两个意思，就能开始改一点东西。HTML、CSS、JavaScript 的入门顺序可以跟着 [MDN 的第一个网站教程](https://developer.mozilla.org/zh-CN/docs/Learn_web_development/Getting_started/Your_first_website) 学。

## 为什么有的事需要“后厨”

展示标题不需要别人帮忙。但请 DeepSeek 回答英语问题，需要网络和 API 密钥。密钥像店里的付款凭证，应该由后厨保管。

浏览器里的页面叫**前端**，负责让人看见和操作。`server.mjs` 等在服务端运行的程序叫**后端**，负责接收请求、检查内容、调用服务。

**Node.js** 是让 JavaScript 在浏览器外也能工作的运行环境。在本机，它让电脑临时成为小服务器；部署之后，同样的程序在托管机器上工作。[Node.js 官方入门](https://nodejs.org/learn/getting-started/introduction-to-nodejs)

“服务器”不一定是一台神秘的大机器。你启动 `node server.mjs` 时，自己的电脑也在提供网站服务。终端窗口关掉或程序停了，本机这个服务就停了。

## 点“发送给 AI”，发生了什么

1. 你写下 “Today I learned how to blink an LED.”。
2. `lounge.js` 把这句话和本房间最近的对话整理成一份小包裹。
3. 包裹交到本站的 `/api/chat`。这个地址不是普通网页，而是办事窗口。
4. `chat-api.mjs` 检查内容是否合适，并在服务端读配置、带上密钥去请求 DeepSeek。
5. DeepSeek 回答，后端把回答交回来。
6. `lounge.js` 把文字放进聊天气泡。

这套“交什么材料、去哪个窗口、会得到什么回复”的约定，叫 **API**。程序发请求用到的 `fetch()`，可以先理解成“去窗口取东西或递材料”。[MDN：使用 Fetch](https://developer.mozilla.org/zh-CN/docs/Web/API/Fetch_API/Using_Fetch)

这里有两个容易混淆的事实：AI 是模型，不是真人外教；本地练习模式不会自动请求 AI。“生成练习报告”也是一次独立的 AI 请求，不是不用网络的评分器。报告可作为复习建议，不应当作标准考试成绩。

## 留言与写日记，为什么不能存成一回事

访客留言是一张**大家共用的留言墙**。浏览器把昵称、正文交给后端，后端再存到 Supabase 数据库。另一个访客打开页面时，也能从那里取到已公开的留言。前提是数据库与服务端配置已完成。

自己的学习日记，更像**放在文件夹里的文章**：内容存成 `posts/` 中的 `.md` 文件。Markdown 是用简单符号排版的文字，例如 `# 标题`、`- 列表`。

浏览器的 `localStorage` 则像**这台设备上的小抽屉**：可以记住练习记录和昵称，但不等于公共数据库，也不会自动出现在你另一台电脑上。浏览器资料被清理后，这些本地内容可能消失。

| 东西 | 当前放在哪里 | 换电脑或刷新会怎样 |
| --- | --- | --- |
| 收藏链接 | 仓库的 `data/resources.json` | 发布后，访客读取同一份文件 |
| 博客文章 | 仓库的 `posts/*.md` | 文件与发布版本保留文章 |
| 本地英语练习记录 | 当前浏览器本地存储 | 同一浏览器可保留，换电脑不自动带走 |
| AI 对话和练习报告 | 当前打开页面的内存 | 刷新后不作为长期档案保存 |
| 留言昵称 | 当前浏览器本地存储 | 方便下次填写，不代表账号登录 |
| 公共留言正文 | Supabase，启用后 | 可供不同访客读取 |

想保留一份 AI 学习报告，就先复制出来，整理成自己的心得。当前网站没有自动把报告变成 Obsidian 笔记的功能。

## 星球为什么能转

你可以把它想成：在屏幕里放一个球，把地球图片包在表面，再从一侧打灯。手指挪动时，程序改变球面的显示角度；连续画很多帧，人眼就看到它转动。

实际代码用的是 WebGL：JavaScript 管角度、拖动和按钮，显卡上的着色器给每个像素计算颜色。当前版本会加载本地地球贴图；贴图未就绪时，还有程序生成的表面备用。它不是一段预录的视频。[MDN：WebGL 教程](https://developer.mozilla.org/zh-CN/docs/Web/API/WebGL_API/Tutorial)

**转动效果与选择页面，是两项配合的工作。** 转到英语目的地只更新说明和链接；点击“开始探索”才跳转。机器不支持 WebGL 时，静态外观和普通入口也能保留使用机会。

这是本项目较难的一块。先学会按钮点击和数组，就已经能理解“换目的地”；地球光照数学留到以后。

## Git、GitHub、Render，各自是哪一间屋

| 名字 | 生活中的比喻 | 真实作用 |
| --- | --- | --- |
| Git | 自带日期和说明的存档本 | 在电脑上记录一批修改 |
| GitHub | 放存档本的网络仓库 | 保存代码、协作、查看历史 |
| GitHub Pages | 展示静态文件的橱窗 | 能提供 HTML、CSS、JS 等文件，不运行本项目 Node 后端 |
| Render | 放着运行中程序的店面 | 可以运行 Node 服务，接待动态请求 |

“保存文件”只是电脑上的内容变了；“commit”是给修改留存档；“push”才把存档传到远端；“部署成功”才说明托管平台运行了对应版本。这四件事不能混为一谈。[GitHub 入门](https://docs.github.com/zh/get-started/using-github/hello-world)、[GitHub Pages 说明](https://docs.github.com/zh/pages/getting-started-with-github-pages/what-is-github-pages)

## 我们开发时，是怎样一步步做的

先把愿望翻译成具体动作：不是只说“我想要社交”，而是说“访客输入昵称与一句话，别人也能读到”。动作清楚，才知道需不需要后端和数据库。

接着划分页面，先让入口能走通，再安排配色、图片、间距。你反馈首页太复杂，就减少入口；你觉得点阵球不够好看，就换成连续球面，后来又改为地球贴图。**每一次反馈都应该变成能检查的变化**，而不只是再加一些特效。

最后分别检查：页面能否打开、链接有没有断、按钮是否真的做事、错误时有没有提示、手机会不会挤出屏幕。接口测试可以用假的服务回答检查程序，不必每次花真实 AI 费用。

## 学完这一篇，试着回答三句话

1. 改标题应该先找 HTML，还是先找数据库？
2. 我在浏览器里记住昵称，别人就能看到我的留言了吗？
3. 我把文章保存到电脑上，线上网站就已经更新了吗？

参考答案：先找 HTML；不能据此判断，留言正文要经过公共存储；没有，还需要整理文章目录、提交与发布。
