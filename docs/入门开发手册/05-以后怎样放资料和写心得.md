# 让网站慢慢装下你的学习

你已经有可以使用的骨架。接下来不必急着增加页面，先分清三种内容：**别人的好资料、自己的理解、动手做过的项目。**

| 内容 | 放在哪里 | 举例 |
| --- | --- | --- |
| 别人的好资料 | `data/resources.json` | Arduino 官方示例、英语文章、视频链接 |
| 自己的理解和心得 | `posts/*.md` | “我终于理解了为什么不用 delay” |
| 项目代码与实践过程 | 代码放 GitHub / `examples/`，过程写文章 | 按键消抖源码、现象、调试记录 |

网站现有的两篇实验文章标明是示例写法。之后请换成你实际做过、观察过的记录；看过示例不等于已经完成实验。

## 添加一条学习资料

先打开 `data/resources.json`。它有 `embedded` 和 `english` 两个数组。数组像一排书，每本书都是一个 `{ … }` 对象。

例如，你确实读过 Arduino 内置示例，想收藏它，可以把下面这个对象加进 `embedded` 数组中，保留原有条目：

```json
{
  "title": "Arduino 内置示例",
  "description": "从 Blink、按键输入到模拟量读取，配合自己的 Uno R3 实验查阅。",
  "url": "https://docs.arduino.cc/built-in-examples/",
  "tag": "官方示例"
}
```

这里的标题是书名，描述是你为什么留下它，网址是书的位置，标签是书脊上的分类。描述最好写你的选择理由，而不只是“很好用”。这个链接对应 [Arduino 官方示例目录](https://docs.arduino.cc/built-in-examples/)。

相邻两个对象之间需要逗号；最后一个对象后面不要多加逗号。JSON 使用英文双引号，不接受中文引号或注释。

改完可以在项目终端检查格式：

```powershell
node -e "JSON.parse(require('fs').readFileSync('data/resources.json','utf8')); console.log('资料格式正确')"
```

然后从本机网址打开嵌入式页面，刷新，实际点一次新链接。格式正确只代表 JSON 能读，不代表链接一定可访问。

英语资料使用同样结构，加入 `english` 数组即可。当前它是空的，所以页面显示等待收藏的提示；不要为了填满界面加入自己没看过的“精选”。

## 写一篇自己的心得：先用文件方式理解原理

1. 复制本手册的 [学习心得模板](模板/学习心得模板.md)，放到项目 `posts/`。
2. 换成独一无二的文件名，例如 `2026-11-24-my-first-study-note.md`。
3. 修改标题、日期、标签、摘要，写下自己的话。
4. 准备展示时，移除开头的 `draft: true`。
5. 运行 `node scripts/build-posts.mjs`，重建文章目录。
6. 在本机博客页与嵌入式实验日志区确认新文章能出现、能打开。

文章开头两行 `---` 中间的内容，叫“元信息”：像贴在本子封面上的标题和日期。例如：

```yaml
---
title: "我今天终于弄懂了什么"
date: 2026-11-24
tags: [学习心得, Arduino]
summary: "用自己的话解释一个刚刚理解的小问题。"
draft: true
---
```

当前解析器支持这种简单的单行字段与行内标签数组。先照这个格式写，不要改成复杂的多行 YAML。`draft: true` 只让目录生成器跳过文章，**不是访问密码，也不是隐私保护**：直接地址和公开仓库仍可能暴露文件。私人内容留在自己的笔记库里，决定公开后再放进网站项目。

`posts/index.json` 相当于文章目录；`posts/*.md` 是正文。漏了重建目录，就像写了一本书，却没有把它加入书架索引。不要手动维护一份容易与正文脱节的目录。

当前所有未标记草稿的文章都会进入同一份目录，嵌入式区也会读取它。若以后英语心得很多，需要另外分栏或筛选，那是后续改造；现在还没有按文章类型自动分配到不同页面的机制。

## 也可以用网页上的写作表单

在本机 Node 服务中打开 `blog.html`，使用写作表单，服务端可生成文章文件并重建目录。此时服务要绑定本机地址；如果提示“只允许本机使用”，不要为了方便公开这个写入接口。

在公网上，写作表单可辅助整理或下载 Markdown，但不会直接替你写入 GitHub。没有作者账号系统，就不应把公共写入当成已完成的功能。当前博客编辑区没有提供跨设备草稿档案；长文先在自己的编辑器里保存一份更稳妥。

博客有自己的简易 Markdown 渲染代码，不是完整 Obsidian。先使用标题、段落、列表、代码块、普通链接。Obsidian 双链、插件语法或 Mermaid 图，不应假设在网站文章页也能自动渲染；保存后实际查看。[Obsidian 基础语法](https://obsidian.md/help/syntax)

## 怎样写得像“自己的理解”

资料收藏回答的是“去哪里看”；心得回答的是“我现在怎样理解”；项目复盘回答的是“我做了什么，证据是什么”。

一篇很短的心得也可以有价值：

> 我原先以为 delay 只是让 LED 暂停。今天发现它会让主循环里的后续代码等着，按键读取也受影响。下一次我想用 millis 计时，同时读取按键，比较两者现象。

这段话只是写法示例，不代表你已经做过这些实验。写自己的笔记时，保留“原先怎么想、实际看见什么、现在怎么理解、还不确定什么”，比大段复制资料更有用。

做硬件项目时，用 [项目复盘模板](模板/项目复盘模板.md)。记录板型、接线、代码版本、预期、实测、错误和修正；界面图片不是接线图，例程也要结合你的实际硬件验证。

## 图片、PDF、代码怎样放

外部资料优先收藏原始链接，并写清来源。自己的代码可放 GitHub，自己的文章放 `posts/`。图片可使用现有 `assets/` 路径。

新增本地 PDF、图片或示例源码时，要同时考虑 `server.mjs` 的文件访问名单。放进文件夹不保证 Render 能访问。不会配置名单时，先请我协助登记具体文件，或先使用一个可公开访问的外部链接；不要把 `E:\…` 本机路径写成给访客的下载地址。

## 从电脑内容到线上内容

```mermaid
flowchart LR
  N[资料与自己的笔记] --> L[选择可以公开的内容]
  L --> F[JSON 收藏或 Markdown 文章]
  F --> T[本机检查链接与页面]
  T --> C[Git 留下提交]
  C --> P[推送 GitHub]
  P --> D[托管平台部署对应版本]
  D --> V[打开线上页面验收]
```

Render 的部署行为取决于服务配置；连接分支并开启相应自动部署时，推送可触发更新。仍要看部署是否成功，不能仅凭 GitHub 有提交就认定页面变了。[Render 部署说明](https://render.com/docs/deploy-node-express-app)

本次只整理文档，没有执行这个发布流程。等你以后明确要发布时，再检查待提交文件，确认 `.env` 和私人笔记没有混进去。

## 与 Obsidian 的关系：先保持简单

可以把 Obsidian 当作私人学习本，网站当作你选出来的公开作品。两边都能写 Markdown，不代表已自动连接。

建议以后先这样使用：在 Obsidian 记录 → 挑一篇适合分享的内容 → 整理图片和链接 → 复制为网站文章 → 预览 → 发布。验收本手册后，我们再决定哪些文档导入 Obsidian。本次没有复制、移动或自动同步你的笔记库。

## 暂停开发后的最小内容计划

不用现在执行，也不设强制打卡。等想继续时，完成三件小事就能让网站更像你：

1. 放一条你亲自用过的学习资料，并说明为什么有用。
2. 写一篇 200–400 字的心得，留下一个还没解决的问题。
3. 做一次小实验，用现象或串口输出证明结果，再写下一步。
