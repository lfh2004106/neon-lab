## 目标

用套件里的 Arduino UNO + 8×32 MAX7219 点阵，做第一个项目：显示一颗爱心，并且会“心跳”。

约束（自己给自己定的）：

- 不装任何第三方库（新手最容易卡在装库上）
- 只用 5 根线
- 上电 3 秒内必须看到"成功了"的信号

## 第一版长什么样

思路很直接：

1. 用字符画描述爱心（8 行 × 32 列，一个字符对一颗灯）
2. 把字符画刷进 `canvas[32]`（一列一个字节）
3. 每个字节写进 MAX7219 的显示寄存器
4. 用 `millis()` 做心跳动画

```cpp
const char *HEART[8] = {
  ".........######..######.........",
  ...
};
```

代码一次编译通过，上电全亮自检也过了——**接线完全正确**。

问题出在图案上。

---

## 现象（第一版）

视频里看到的是：

- 中间两片亮，两边两片黑（位置对：爱心确实画在中间）
- 但形状是**两块互不相干的亮斑**
- 左半边"上宽下窄"，右半边"上窄下宽"
- 形状 1.35 秒内一次没变，只有亮度在变

最后一条当时误导了我：以为"形状不变"是动画设计问题（其实那正是我把动画改成只调亮度之后的样子）。

---

## 五次假设，四次错

### 假设 1：图案太小太暗，看不清

**做法**：把"大小两帧"改成"始终一颗大爱心 + 亮度脉动"。

**结果**：效果确实更好看了，但"不像爱心"没解决。

**学到**：先别急着改设计，先确认"到底显示的是什么"。

---

### 假设 2：某一片模块装反了（180°）

**依据**：左半边和右半边的形状"方向相反"，像是其中一片被转了 180°。

**验证**：写"1/2/3/4 个点"测试——每片亮不同数量的点，就能看出片序和方向。

**结果**：用户回 **4-3-2-1，都在最上面**。

- 4-3-2-1 → 数据是从右端进去的，**整幅画面左右镜像**
- 都在最上面 → **四片的行方向都正常**，没有装反

**结论**：假设 2 错。而且镜像对左右对称的爱心**完全无害**（爱心镜像后还是爱心），所以这不是原因。

---

### 假设 3：某一片的列方向反了

**验证**：写 L 形测试码（竖条在左、横条在下）。如果某片列反了，它的 L 会变成镜像。

**结果**：四个 L 一模一样、都正着。

**结论**：假设 3 错。

**但这里埋了一个大坑**：L 是"一整行 + 一整列"。**整行整列在转置之后还是整行整列**，所以这个测试对转置问题**完全免疫**。它给了我一个"硬件没问题"的假安全感。

---

### 假设 4：是两块板之间的物理接缝造成的

**依据**：两块 8×8 之间有拼缝，爱心又被切成两半，看起来就是"被接缝劈开"。

**验证**：看 L 测试的底边——四个模块连成一条**完整不断的横线**。

**结论**：接缝不影响显示，假设 4 错。

---

### 假设 5（正确）：图像被转置了

用户那句提示是关键：

> "你是不是代码中写的位置写错了。这是 8 乘 32 的点阵"

这句话让我从"硬件坏了"转到"我是不是把**地址模型**搞错了"。

重新检查：**这块板每片的 8 个寄存器（0x01–0x08）接的是 8 行，不是 8 列**；字节的 8 个 bit 才是 8 列。

也就是说：我按"寄存器 = 列"写，硬件按"寄存器 = 行"读 → 每一片都把图像**转置**了一次。

**这完美解释了现象**：

- 爱心转置后，左右两半各自旋转 90° → 两块"方向相反"的亮斑 ✓
- 转置是整体变换，不影响"亮/灭总数"和"位置在中间" ✓
- 行方向、列方向测试都正常（转置不改变整行整列）✓

---

## 怎么确认的（可复用的方法）

把"代码应该输出的图案"和"照片里实际的图案"**逐颗对比**：

```python
expected[r][c] = (HEART[r][c] == '#')
actual[r][c]   = 照片里第 r 行第 c 列亮不亮
print("不一致的灯数：", sum(expected != actual))
```

再把期望图案用圆圈**叠在照片上**，一眼就能看出差异集中在哪：

- 中心区域全对、边缘零星不符 → 映射对，只是采样误差
- **左右两半形状互为反方向** → 转置

> 这一步花的时间最多（要处理透视、过曝、手机旋转），但它是唯一能给出**确定结论**的方法。光靠"看着像不像"，永远在猜。

## 修复

`show()` 里发数据前先转置：

```cpp
// 原来：寄存器 d ← 第 d 列的 8 个 bit（按列写）
// 现在：寄存器 r ← 第 r 行的 8 个 bit（转置后再发）
for (uint8_t r = 0; r < 8; r++) {
  uint8_t bits = 0;
  for (uint8_t b = 0; b < 8; b++)
    if (canvas[c * 8 + b] & (1 << r)) bits |= (1 << b);
  maxWrite(c, r + 1, bits);
}
```

改完编译 2076 B / 6%，RAM 290 B / 14%。

## 复盘

### 做对了什么

1. **先让它亮起来**：第一版不做任何"高级效果"，只求点亮、只求能编译。
2. **每一步都有成功信号**：全亮 1 秒、"四片都亮"、编译占用百分比——每一步都能立刻判断"过没过"。
3. **用真编译验证**，不是"看起来对"。每次改完都真编译一次，避免上传才发现语法错误。
4. **把期望值和实际值并排对比**（叠图），而不是凭感觉判断。
5. **动画设计上做了减法**：从"两帧大小变化"改成"只调亮度"，代码更短、效果更稳。

### 走了什么弯路

1. **连续三次假设"硬件坏了"**。新手最容易怀疑硬件，其实硬件出问题的概率远低于代码。
2. **测试图案设计有缺陷**。整行整列的 L 测不出转置——测不出不等于没问题。
3. **测量方法不稳定**。用等间距网格去读透视照片，误差大到能"制造"出不存在的现象（比如"中间缺两列"）。前后换了 5 种网格才读准。
4. **没有第一时间怀疑"地址模型"**。当现象是"整体变换"（不是缺、不是乱）时，第一个该怀疑的就是**行列/坐标系定义**。

### 如果重来一次（30 分钟版）

```
1. 先写"只亮左上角一颗灯"的 4 行程序 → 确认行列方向
2. 再写"一条对角线" → 确认有没有转置（对角线转置后方向会变）
3. 再写"整屏全亮 + 一个缺口" → 确认 4 片都对
4. 最后才画爱心
```

**一个点、一条对角线**就能在 5 分钟内确定全部映射关系。这个项目用了 4 小时，一大半花在没有先做"最小可辨识图案"。
